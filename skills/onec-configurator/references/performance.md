# Производительность и диагностика

## От симптома к измерению

Зафиксировать действие, время, объём данных, пользователя, клиента, сборку
платформы, СУБД, ожидаемое время и воспроизводимость. Различать холодный/тёплый
кеш, сеть, блокировку, процессор, запрос БД и отрисовку формы.
Не приписывать задержку СУБД без наблюдений.

Выбрать минимальный инструмент: замер производительности, технологический
журнал, журнал регистрации, лог интеграции, план/статистика запроса в тестовом
контуре. Журнал регистрации фиксирует прикладные события, а не заменяет
техжурнал ожиданий и длительных операций.

## Что проверять

| Симптом | Проверка |
|---|---|
| Медленное открытие формы | Число серверных вызовов, объём передаваемых данных, динамический список |
| Долгая обработка пачки | N+1 запросы/объекты, вложенные циклы, чтение через ссылки |
| Длительный запрос | Селективность, кардинальность соединений, временные таблицы, индексы |
| Зависание записи | Блокировки, порядок захвата, длительность транзакции, внешний I/O |
| Периодический сбой обмена | Таймауты, повторная доставка, размер сообщения, параллельные задания |
| Рост памяти | Полная выгрузка результата, копии коллекций, длительность жизни кеша |

Для техжурнала выбирать события и свойства по документации целевой платформы;
не выдавать случайный logcfg.xml за универсальный. Ограничивать сбор по времени
и процессам. Полные тексты запросов/параметры могут содержать данные пользователей.

## Эксперимент

Менять один существенный фактор, повторять одинаковый сценарий на одном
снимке данных, считать количество запусков, время, строки/суммы и ошибки.
Сравнивать распределение времени, а не один удачный запуск. Ускорение без
равенства результата не считается исправлением.

Индексы проектировать по реальному отбору/соединению и стоимости записи.
Не переносить настройки PostgreSQL на MS SQL Server и наоборот. Не выполнять
изменение системных таблиц 1С или DDL напрямую ради «быстрой оптимизации».

## Разбор ошибки

Прочитать полное сообщение и цепочку вызовов, найти первую причину, сверить
метаданные/типы/контекст. Для зависания проверить модальный диалог, ожидание
блокировки и процесс, а не просто повторять команду. После одинакового отказа
изменить гипотезу на основании наблюдений; не запускать бесконечные повторы.

Исправление сопровождать воспроизводимым сценарием: вход, шаг, ожидаемое,
полученное, версия, доказательство после правки. Если стенда нет, сформулировать
проверяемую гипотезу и необходимые измерения без обещания процента ускорения.
