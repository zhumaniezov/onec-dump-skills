# БСП и прикладные конфигурации

## Подтвердить реальную библиотеку

Установить версию БСП по проекту и поставке. Одно имя общего модуля не доказывает
версию или полноту внедрения. Национальная локализация, Альфа-Авто и самописная
конфигурация могут менять публичный интерфейс; не подставлять API БП РФ в БП УЗ.

Перед использованием метода найти его определение, `Экспорт`, параметры,
контекст модуля, описание результата и хотя бы одно актуальное место вызова.
Проверить переопределяемые точки и обработчики, которые должна реализовать
конфигурация. Пример БСП 3.2 не считать доказательством для проекта на 3.1.7.

Суффиксы Клиент, КлиентСервер, ВызовСервера, ПовтИсп помогают навигации;
окончательное решение принимать по свойствам модуля и телу метода.
Служебный API не подменять публичным по совпадению назначения. Переопределяемый
модуль — точка внедрения, а не универсальная библиотека прямых вызовов.

## Сначала существующий механизм

| Задача | Проверить в проекте |
|---|---|
| Длительная операция | Фоновые/длительные операции, получение результата, отмена |
| Печатная форма | Менеджер печати, коллекция форм, области, права |
| Внешняя обработка | Регистрация, версия интерфейса, команды и безопасный режим |
| Доступ и пользователи | Группы/профили, параметры сеанса, действительные права |
| Обмен | Узлы, регистрация изменений, сценарии, расписание и журнал |
| Файлы/JSON/HTTP | Доступные API платформы и БСП с их контекстами |
| Обновление данных | Штатные обработчики обновления, повторяемость и версия |

Не придумывать удобное имя функции. Если метода нет, явно выбрать другой
существующий API, небольшой собственный метод или версионный адаптер.
Словарь стороннего проекта полезен для поиска, но установленный код важнее.

## MVP и перенос механизмов

Для внедрения небольшой функции составить минимум объектов и зависимостей.
Отдельно оценить минимальную платформу и совместимость самой библиотеки.
Не выдавать перенос формы настроек за перенос рабочего механизма.
Кнопка ручного запуска и регламентное задание должны вызывать один понятный
прикладной сценарий; хранение настроек, состояние и ошибки проверить отдельно.

Если пользователь разрешил дубли, небольшую автономную функцию можно перенести
под новым именем, сохранив необходимые зависимости. Отметить происхождение и
проверки. Не считать дубль поводом создавать много общих модулей. Существующий
модуль подходящего назначения предпочтителен при совместимом контексте.

При замене механизма обмена сохранить идентификаторы узлов, очередь регистрации
и протокол подтверждения, если задача не требует миграции этих данных.
Внедрение библиотеки через копирование метаданных не гарантирует её готовность:
проверить регистрацию подсистем и обработчики внедрения.

## Типовые конфигурации

Прочитать правила поддержки, маркировки доработок и обновления. Не снимать
поддержку и не включать изменение объекта без задачи. Для расширения проверить
доступность перехвата и применимость, для прямой правки сохранить минимальный diff.
Не менять учётную методику по техническому удобству; бизнес-правило подтвердить
задачей и контрольными данными.
