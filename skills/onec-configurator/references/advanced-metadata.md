# Другие виды метаданных и прикладные механизмы

## Универсальная проверка

Для любого объекта определить класс, владельца, свойства, типы, дочерние
объекты, синонимы, формы, команды, права и зависимости. Специфика класса важнее
похожего XML. Генератор, поддерживающий 23 типа, не гарантирует поддержку всех
объектов платформы. Каркас сверять с той же версией Конфигуратора.

## Учётные объекты

| Объект | Что установить до изменения |
|---|---|
| План счетов | Виды счетов, иерархия, признаки учёта, субконто, предопределённые счета |
| Регистр бухгалтерии | План счетов, корреспонденция, измерения, балансовые/небалансовые ресурсы, признаки учёта |
| План видов характеристик | Тип значения, дополнительные значения, владельцы, предопределённые характеристики |
| План видов расчёта | Базовый период, вытеснение, зависимости расчётов и предопределённые виды |
| Регистр расчёта | Период действия/регистрации, базовые периоды, перерасчёты, измерения и ресурсы |
| Последовательность | Регистраторы, границы актуальности, восстановление последовательности |

Не заменять бухгалтерские движения движениями регистра накопления только
по сходству полей. Для субконто проверить типы, порядок и признаки ведения.
Для расчётов различать фактический период действия, регистрацию и базу;
повторный расчёт и перерасчёт имеют отдельную логику. Конкретную методику
зарплатного/бухгалтерского учёта брать из конфигурации и требований задачи.

Новый предопределённый элемент и переименование существующего — разные
операции. Сохранить идентичность и проверить обращения по имени, ссылке,
XDTO/обмену и установленным настройкам. Изменение типа характеристики может
затронуть уже сохранённые значения и составные типы других объектов.

## Событийная модель

Подписка: источник, событие, обработчик, его экспортность и сигнатура,
порядок взаимодействия с обработчиком объекта и возможные повторные вызовы.
Не считать поиск только в ObjectModule полным анализом записи объекта.

Регламентное задание: метод, параметры, ключ, использование, расписание,
пользователь и запрет параллельности. Его алгоритм не должен зависеть от
открытой формы/диалога. См. `integrations.md`.

Константа/опция: тип, хранение, привязка опций, параметры опций и обновление
UI/сеансового кеша. Изменение параметра может требовать обновления интерфейса
или сеанса, что нужно проверить в используемом клиенте.

## Бизнес-процессы и задачи

Проверить карту маршрута, точки действия/условия/разделения/слияния,
адресацию задач, исполнителей, права, состояние и события переходов.
Завершение задачи может запускать следующие действия; прямая запись статуса
не всегда эквивалентна штатному выполнению. Проверить повтор, отказ,
параллельные ветки и недоступность исполнителя на тестовых данных.

## Прикладные данные и временное хранение

Для временного хранилища определить владельца и срок жизни адреса, контекст
клиента/сервера и допустимость передачи в фоновое задание. Путь локального
файла клиента не является путём сервера. Файл сервера может отсутствовать
на другом рабочем процессе/узле кластера. Использовать подходящий механизм
передачи файлов целевой версии и освобождения временных ресурсов.

Для истории данных, разделения данных, мобильного/автономного режима сначала
проверить включённые свойства, версию и ограничения платформы. Не обещать
поддержку экзотического объекта без его эталона и платформенного сценария.
