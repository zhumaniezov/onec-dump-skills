# Интеграции и фоновые операции

## Сначала контракт

Установить источник/получатель, владельца данных, стабильный идентификатор,
направление, протокол, схему, версию, время, локаль, правила удаления и повторов.
Различать UUID ссылки 1С, внешний идентификатор и строковое представление.
Не сопоставлять контрагентов/номенклатуру только по названию без правила уникальности.

## HTTP и JSON

Проверить методы и маршруты, коды ответа, Content-Type/charset, таймауты,
размеры, пагинацию, аутентификацию, формат ошибок и корреляционный идентификатор.
Сериализовать JSON штатным API соответствующей версии, не конкатенацией строк.
Типы дат, чисел, булевых и null согласовать с контрактом, особенно для UZS/RUB
и ссылочных полей. Не зависеть от пользовательской локали форматирования.

Изменение ответа «всегда 200» на другие коды требует согласования контракта
с потребителями, даже если новая схема привычнее. Технический повтор допустим
для определённых ошибок и идемпотентных операций; не повторять POST с побочным
эффектом без ключа/механизма идемпотентности.

Не отключать проверку TLS для исправления сетевой ошибки. Секреты получать
из разрешённого хранилища, в журнал писать достаточно данных для диагностики,
но не пароль и полное содержимое персональных данных.

## XML/XDTO

Проверить namespace URI, схему, типы, nil/отсутствующие элементы, кратность,
порядок, дату/число и кодировку. Экземпляр XML, XSD и пакет XDTO — разные сущности.
Не путать префикс namespace с URI. Выполнить сериализацию и обратное чтение
на контрольном сообщении, включая неизвестное/отсутствующее поле и неверный тип.

При изменении пакета XDTO проверить все зависимые сервисы, обработчики и версии
схемы. Отсутствие ошибок обычного XML-парсера не подтверждает XDTO-валидность.

## Очереди и планы обмена

Определить момент регистрации изменений, состав сообщения, подтверждение,
повторную доставку, порядок, потерю связи, отложенную обработку и удаление.
Не очищать регистрацию до подтверждённого успешного завершения нужной стадии.
Сохранить UUID узлов и состояние очереди при адаптации существующего обмена.

Разделять доставку и применение. Для приёмника обеспечить идемпотентность
или явно описанный эффект повторной доставки. Не держать транзакцию базы
открытой во время длительного сетевого запроса. Обработать частичный успех:
сообщение отправлено, но ответ потерян; данные применены, но подтверждение не дошло.

## Фоновые и регламентные задания

Фоновое выполнение не имеет UI-контекста. Проверить параметры, пользователя,
права, доступность каталога на сервере, ключ параллельности и журналирование.
Ручной запуск и расписание должны проходить через согласованный алгоритм,
без скрытого расхождения параметров и обработчиков ошибок.

Повторять после сбоя с понятной контрольной точки; не считать «задание запущено»
успешным выполнением. Проверить результат, ошибки, блокировки и запрет
одновременного запуска, если он нужен по бизнес-смыслу.

## Конвертация данных

Различать правила КД 2.x и КД 3.x. Сначала установить формат, версию, объекты
правил и их обработчики в реальном проекте. Не переносить названия и события
из одной технологии в другую по сходству. Проверить регистрацию, конвертацию
ссылок, порядок зависимостей, удаление, повторный обмен и обратное чтение правил
штатным редактором. Комплект не содержит универсального парсера правил КД.
