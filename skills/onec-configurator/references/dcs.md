# Система компоновки данных

## Сначала восстановить модель отчёта

Прочитать метаданные отчёта и основной макет СКД. Найти наборы/источники данных,
запросы, связи наборов, параметры, поля и их типы, вычисляемые поля, ресурсы,
варианты настроек, группировки, выбор/отбор/сортировку, условное оформление.
Проверить модуль отчёта, форму и код изменения настроек при компоновке.
Схема, настройки, макет компоновки и результат — разные сущности.

Для каждого нового поля проследить цепочку:
**источник → псевдоним запроса → поле набора/dataPath → выражение/ресурс →
выбранное поле/группировка/вариант → пользовательская настройка**.
Добавление поля только в SELECT не гарантирует его появление в отчёте.

## Таблица проверок

| Изменение | Связанные места |
|---|---|
| Поле запроса | Псевдоним, тип, поле набора, автозаполнение, варианты |
| Параметр | Тип, значение/выражение, обязательность, использование, доступность |
| Вычисляемое поле | Доступность исходных полей, деление на ноль, Null, уровень вычисления |
| Ресурс | Выражение, группировки расчёта, корректность общих итогов |
| Связь наборов | Ключ, кратность, параметры связи, пустые наборы |
| Группировка | Поля, порядок, иерархия, детализация, выбор на каждом уровне |
| Отбор | Тип операнда, сравнение, доступность поля, место применения |
| Вариант | Настройки по умолчанию и сохранённые пользовательские варианты |

Проверять, что изменение названия не оставило старый dataPath в оформлении или
вложенной группировке. Идентификаторы пользовательских настроек сохранять там,
где надо сохранить их существующие привязки.

## Итоги и выражения

Средняя цена и процент маржи обычно требуют расчёта из агрегированных величин;
простое суммирование/усреднение процентов не обосновывать названием ресурса.
Проверить формулу на данных с разным весом строк и при нулевом знаменателе.
При детализации по новому измерению проверить, не размножились ли суммы.

Язык выражений СКД, язык запросов и BSL различаются. Метод BSL нельзя просто
вставить в выражение СКД без поддерживаемого механизма и соответствующего
контекста. Точные функции/уровни вычисления проверять по документации платформы.

## Запрос СКД

Проверка запросов схемы и полей по метаданным: `onec_query.py scan <папка отчёта>` (см. queries.md).
«Где используется» с учётом запросов СКД — `onec_index.py refs` (связи вида `query`).


Расширения языка СКД в фигурных скобках не переносить в обычный Запрос без
разбора. Проверить автозаполнение полей и то, куда система помещает отбор.
Для виртуальных таблиц применять правила `queries.md`. Отборы, параметры
данных и пользовательские настройки не взаимозаменяемы.

Если вычисленное поле получило имя исходного поля, проверить фактически
сформированный запрос и место применения отбора. Не считать совпадение
псевдонимов безусловно безопасным или безусловно ошибочным.

## Редактирование XML

Сохранить namespace, `xsi:type`, типизированные значения, локализованные строки
и структуру коллекций. В XML-тексте запроса амперсанд параметра экранируется
как `&amp;`, если узел не использует CDATA. Не экранировать повторно при записи
через корректный XML API. Не переименовывать namespace-префиксы вслепую.

Использовать аналогичный узел того же файла/формата; универсальная сериализация
может изменить весь документ. Инспектор комплекта проверяет только XML,
а не модель СКД, выражения или типизацию значений XDTO.

## Приёмка отчёта

1. Загрузить XML и прочитать схему средствами платформы/Конфигуратором.
2. Выполнить каждый затронутый вариант с заполненными и пустыми параметрами.
3. Сверить детали и итоги с независимым контрольным запросом/источником.
4. Проверить отбор, порядок, оформление, расшифровку и сохранённые настройки.
5. Повторить с целевыми правами, несколькими организациями и пустой выборкой.
6. Проверить длительность на реалистичном объёме и повторную выгрузку.

XML parse и отсутствие ошибок BSL не означают, что отчёт компонует данные.
