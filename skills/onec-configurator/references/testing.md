# Автотесты 1С и OneScript

## Навигация

- Выбор слоя и инструмента

- Vanessa Automation и Vanessa-ADD

## Выбор слоя и инструмента

Что установлено — `onec_env.py discover`. Ничего не устанавливать самому: назвать пользователю
инструмент, зачем он нужен и откуда взять, и продолжить без него.

| Инструмент | Нужен для | Где взять |
|---|---|---|
| Платформа 1С + тестовая база | проверки, сборки, любых автотестов | у пользователя |
| YAxUnit | модульные тесты; запуск профилем `yaxunit` без OneScript | выпуски github.com/bia-technologies/yaxunit (`.cfe`) |
| Vanessa Automation | UI-сценарии | выпуски github.com/Pr-Mex/vanessa-automation (`.epf`) |
| OneScript (+ `opm`) | vanessa-runner, OneUnit, `.os`-скрипты | oscript.io, github.com/EvilBeaver/OneScript |
| vanessa-runner | шаблоны `assets/pipelines` (`vrunner`) | `opm install vanessa-runner`; 3.x — OneScript 2.0+; шаблоны под 3.0.2 |

Для «собери», «проверь на платформе» OneScript не требовать: это `onec_env.py profile`.

Запуск без OneScript — готовые профили `onec_env.py profile cf-check | yaxunit`
(pipeline.md, «Быстрый путь»). Если автотестов в проекте нет, проверка Конфигуратором
их не заменяет: сообщить об этом и дать шаги ручной проверки.

Сначала прочитать существующие tests, зависимости и команды CI. Использовать
принятый движок, если он покрывает задачу. Не внедрять все фреймворки сразу.

| Задача | Подход |
|---|---|
| Функция/модуль BSL, объектная модель, запрос | YAxUnit внутри 1С; существующий xUnit/Vanessa-ADD также допустим |
| Пользовательский процесс, форма, команды | Vanessa Automation; существующие UI-тесты проекта |
| Обычные формы/старая платформа | Проверить поддержку режима в выбранном движке; возможно xUnit/Vanessa-ADD или свой EPF |
| OneScript-скрипт, библиотека, CLI | OneUnit либо используемый 1testrunner |
| HTTP/обмен/контракт JSON | Тест внутри 1С или внешний клиент, контролируемый сервер/фикстуры |
| XML и файлы выгрузки | Инспектор/собственные Python-тесты плюс последующая проверка платформой |
| Сборка и запуск всех перечисленных | Собственный pipeline.py либо существующий CI/vrunner |

OneScript — отдельная среда. Успешный .os-тест не подтверждает поведение
Документы, РегистрыСведений, Запрос, управляемой формы и транзакций платформы.

## YAxUnit

Работает в расширении; EDT для запуска не нужен. Установить совместимый движок
и отдельное расширение с тестами в **тестовую** ИБ. Учитывать ограничения
заимствования и видимость экспортных методов, клиентские/серверные контексты.
В документации движка требуются соответствующие настройки безопасности
расширения для работы с файлами; настраивать только тестовый стенд.

Тестовый модуль регистрирует экспортные сценарии в `ИсполняемыеСценарии` через
`ЮТТесты`. Утверждения доступны через `ЮТест.ОжидаетЧто(...)`. Методы фикстур,
мокирования, транзакций и регистрации сверять с установленной версией.
Шаблон `assets/test-templates/YAxUnit.bsl.example` требует реального прикладного
API проекта; не включать незаполненный пример в собираемое расширение.

Два маршрута запуска:

- Платформа: `ENTERPRISE ... /C RunUnitTests=<путь-к-json>`.
- vanessa-runner 3.0.2: `test yaxunit --ext <тестовое-расширение>` с JUnit.

JSON-профиль задаёт отбор тестов, путь JUnit, файл результата, закрытие клиента.
Примеры в `assets/pipelines/test-yaxunit.example.json` и `full-cycle.example.json`.
Первый предполагает уже подготовленную ИБ; второй собирает и загружает тесты.
Расширение движка не содержит тесты бизнес-логики автоматически.

## Vanessa Automation

Функциональные сценарии описывают действие пользователя и проверяемый результат.
Шаги брать из реальной библиотеки установленной версии или записывать тестовым
клиентом, затем приводить к устойчивому сценарию. Подписи формы и доступность
команд зависят от локализации, прав и состояния данных.

Маршрут: клиент-менеджер `/TESTMANAGER`, `/Execute <vanessa-automation.epf>`,
`/C StartFeaturePlayer;VAParams=<json>`. Настроить клиентов тестирования,
разные порты для параллельных запусков, каталог feature, JUnit и закрытие
TestClient. Отдельно задать `ЗавершитьРаботуСистемы: true` для завершения
TestManager; закрытие TestClient не заменяет этот параметр. Для веб-клиента —
отдельный поддерживаемый режим и окружение.

`test-vanessa-automation.example.json` создаёт VAParams с новым каталогом JUnit.
Указанная ИБ должна быть тестовой и подготовленной; профиль не создаёт её.
Для CI нужна действующая графическая сессия там, где её требует клиент.
Первичную установку компонентов/диалоги выполнить при подготовке стенда.

Не считать Pending успешным тестом. В примере включено `ПриравниватьPendingКFailed`.
Ожидать конкретное состояние/элемент с таймаутом; не лечить гонки бесконечными
ожиданиями и повтором всего сценария. Сохранять скриншот и логи при ошибке,
учитывая наличие данных пользователя на снимках.

**Vanessa-ADD — другой проект.** В изученной версии vanessa-runner команда
`test vanessa` предназначена для `bddRunner.epf` и VBParams Vanessa-ADD.
Не подставлять автоматически обработку Vanessa Automation в этот маршрут.
Для существующего ADD использовать его документированный запуск и отчёты;
`test xunit` — модульные/дымовые тесты ADD, а не универсальный API YAxUnit.

## OneScript

Проверять установленную среду, packagedef, локальные зависимости и oscript.cfg.
Для новых инфраструктурных тестов подходит OneUnit; для существующих наборов
сохранить 1testrunner. Не переносить новые аннотации на старый runtime вслепую.

OneUnit: `execute --directory <tests> --junit <новый-файл>`; `discover` помогает
проверить обнаружение тестов до прогона. Пример использует явный oscript и
`oneunit/src/cli/main.os`, чтобы не зависеть от Windows .cmd-обёртки.
На исследованной ветке OneUnit packagedef требует OneScript 2.2.0; закрепить
конкретные версии проекта. Минимум vanessa-runner 3.0.2 по его README — 2.0.0;
более новая ветка develop требует уже другую версию. Не смешивать требования.

1testrunner: использовать команду и формат отчёта установленного пакета
(`-runall`, xddReportPath и другие параметры зависят от версии). Исследованная
страница проекта подтверждает этот маршрут; необследованный пакет не включать
в автоматический профиль по выдуманному пути.

Проверять фактическое поведение скрипта: кириллица/пробелы в пути, отсутствующий
файл, ошибочный процесс, таймаут, кодировка, повторный запуск. Подменять только
внешнюю дорогую зависимость, сохранять реальные файловые/процессные границы теста.

## Данные и фикстуры

Каждый сценарий определяет минимальные данные, идентификатор прогона и очистку.
Обмены, задания и уведомления тестовой копии направить в локальные заглушки
или отключить по правилам стенда. Не отправлять тестовые письма/платежи наружу.

Транзакционный откат подходит не всем сценариям: другой сеанс, фоновое задание,
HTTP, файл и внешняя система не откатываются вместе с текущей транзакцией.
Для UI/обменов использовать отдельный набор данных или восстанавливаемую копию.
Для тестов ограниченных прав запускать соответствующего пользователя; не
компенсировать отсутствие прав привилегированным режимом.

Сравнивать движения/регистры до и после по полному ключу. Для записи проверять
повторяемость, коллизии и сохранность незатронутых данных. Блокировки/гонки
проверять независимыми сеансами с согласованной точкой старта; файловая ИБ
не подтверждает поведение PostgreSQL/MS SQL на целевом сервере.

Запросы: эталонные ключи и суммы, размножение при соединении, границы периода,
Null/пустая ссылка, несколько организаций, RLS. СрезПоследних проверять на
изменении неключевого реквизита между записями. СКД: выполнить схему, сравнить
детали и общие итоги; среднюю маржу проверить на строках с разным весом.

## Свои тесты

Допускается небольшой EPF/расширение/внешний клиент, если полноценный фреймворк
избыточен. Нужны именованные кейсы, assertions, fixture/cleanup, ловля исключений
с провалом, конечный таймаут и машинный отчёт. Не писать «PASS» без проверки.
Не глотать исключения и не превращать ошибку создания данных в пропуск.

Контракт pipeline.py: процесс завершается; пишет свежий JUnit с testcase на
каждый кейс; failures/errors отражают ошибку; skipped задан явно. Ненулевой
exit code — провал. Для своего адаптера сначала показать, что намеренно
ошибочное ожидание приводит к красному прогону и ненулевому коду pipeline.

## Критерий успеха

Проверить найденные/выполненные тесты, ошибки и пропуски. Успех — реальные
assertions плюс отчёт **этого** запуска. Установить ожидаемый минимум тестов,
не удовлетворяться одним случайно найденным кейсом. Пропуск важного сценария
должен блокировать принятие результата. Allure удобен для просмотра, но его
наличие без анализа статусов не доказывает успех.
