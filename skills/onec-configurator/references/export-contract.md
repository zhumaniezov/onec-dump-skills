# Полная и инкрементальная выгрузка

Это контракт файловой разработки через Конфигуратор. Не переносить правила
Git-конвертера EDT на такой проект автоматически. Доступность ключей сверять
со справкой выбранной платформы; ниже проверены описания 8.3.27 и история
механизма инкрементальной выгрузки.

## Что различать

| Операция | Вход | Результат/проверка |
|---|---|---|
| Полная DumpConfigToFiles | Конфигурация или выбранное расширение | Новый каталог файлов |
| DumpConfigToFiles -update | Каталог с актуальным ConfigDumpInfo | Обновлённая выгрузка |
| -getChanges | База сравнения версий | Список изменений, не Git diff |
| Выгрузка -listFile | Список **объектов** | Учитывать вложенные объекты явно |
| Загрузка -files/-listFile | Список **файлов** | Загрузить полноту зависимостей |
| LoadConfigFromFiles | Выгрузка | Редактируемая конфигурация |
| UpdateDBCfg | Проверенная конфигурация | Изменение конфигурации БД |

Hierarchical — основной маршрут; Plain существует, но его структуру нельзя
считать иерархической. Для частичной загрузки уточнить Format. AllExtensions
обрабатывает расширения по подкаталогам, основная конфигурация — отдельная цель.

В CLI `-update` требует подходящего файла версий; `-force` разрешает полный
fallback вместе с update. Внешний `-configDumpInfoForChanges` задаёт базу
сравнения, сам не обновляется; при таком формировании пакета нужен пустой
выходной каталог. Не скрывать отсутствие базы версий принудительным режимом
без понимания, что получится полная выгрузка.

ConfigDumpInfo.xml обслуживает механизм версий. Не придумывать configVersion,
не удалять файл и не добавлять его в .gitignore как универсальное «исправление».
Политику хранения согласовать с существующим циклом проекта. После загрузки
доступен `-updateConfigDumpInfo`; актуальность подтверждать штатной выгрузкой.

## Список изменений не является сценарием применения

Файл getChanges имеет кодировку UTF-8; пустой файл означает отсутствие
обнаруженных изменений. Единственная строка FullDump означает необходимость
полной выгрузки. Не парсить его как список путей к XML. Для других строк
проверить все виды изменений по руководству конкретной версии, включая
переименование/удаление. Не реализовывать удаление как угадывание имени файла.

Для нового объекта одновременно проверить состав владельца, определения,
модули/формы/макеты, роли/подсистемы и ссылки. Переименование — изменение
связанного набора файлов и ссылок при сохранении идентичности объекта.
Удаление файла из Git само по себе не доказывает удаление объекта из ИБ.

## Практический протокол

1. Зафиксировать снимок исходников и версию платформы/формата; исключить
   одновременную выгрузку из другого Конфигуратора в этот каталог.
2. Сделать файловую правку и минимальный diff; служебные версии не изобретать.
3. Для неизвестного состояния развернуть **полную** выгрузку в отдельной ИБ.
4. Проверить, обновить БД и выполнить соответствующие тесты.
5. Повторно выгрузить отдельно. Сравнить SHA, BOM/EOL, UUID, состав и смысл.
6. Если повторная сериализация внесла изменения, классифицировать их.
   Не добавлять глобальное игнорирование расхождений ради зелёного отчёта.

`-NoCheck`, `-ignoreUnresolvedReferences` и пропуск проверки не являются лечением
нарушенной целостности. `-partial` из новых руководств не считать доступным
в каждой старой сборке. Работа с пакетами требует отдельного теста add/rename/
delete на целевой версии до применения к реальному проекту.
