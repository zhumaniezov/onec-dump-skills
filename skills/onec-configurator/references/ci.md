# CI, стенды и поставка

## Три контура

1. **Быстрый.** Diff/инспектор, BSL LS, тесты Python/OneScript. Не требует
   запускать всю конфигурацию при изменении документации.
2. **Платформенный.** Чистая ИБ, загрузка, CheckConfig, обновление БД,
   CF/CFE/EPF/ERF, применимость, модульные и интеграционные тесты.
3. **Сценарный.** Целевые роли/клиенты, UI, СКД, обмены, отдельный серверный
   прогон для конкуренции/производительности. Объём зависит от задачи.

Составить матрицу платформа/совместимость/основная конфигурация/БСП/клиент/СУБД.
Новая сборка платформы не подтверждает старую. По возможности каждый job имеет
свою ИБ, run directory, TestClient-порт и набор тестовых данных.

## Агент выполнения

Установленная и лицензированная платформа, закреплённые OneScript/vrunner,
движки тестов и служебные EPF. Установку выполнять отдельно от каждого теста.
Не копировать дистрибутивы 1С/HBK в публичный Git. Для UI обеспечить требуемую
интерактивную сессию; обычный headless Linux runner не заменяет Windows-клиент.

Настроить проектный профиль вместо редактирования скилла под каждый стенд.
В поставке есть пример GitLab job `assets/ci/gitlab-ci.yml.example` для
Windows shell executor. Метки runner условные; включать после настройки стенда.
Для GitHub Actions использовать тот же вызов на self-hosted runner, сохранить
exit code, добавить upload результатов с условием always. Скилл не требует CI.

Код из неподтверждённых внешних PR не запускать на runner с доступом к рабочим
ИБ/секретам. Это ограничение конкретного окружения, а не причина блокировать
обычную локальную разработку по поручению пользователя.

## Приёмка отчётов

Проверять код pipeline и отчёты фреймворка, ожидаемое количество тестов,
ошибки/пропуски. Показывать причину skipped/blocked. Срок хранения отчётов
назначить по проекту; stdout не считать более надёжным, чем JUnit и состояние ИБ.
Не делать allow_failure для обязательной проверки и не игнорировать ошибку
нативного процесса в PowerShell. После вызова проверить `$LASTEXITCODE`.

Allure/JUnit собирать из нового каталога прогона, не смешивать старые результаты.
Покрытие собирать поддерживаемым инструментом; зафиксировать исключения и слой.
Процент покрытия не заменяет тест бизнес-инварианта и не выводится из числа тестов.

## Пакет поставки

Артефакты CF/CFE/EPF/ERF, SHA-256, ревизия исходников, точные версии сборочных
инструментов, профиль с удалёнными секретами, протокол проверок, ограничения,
инструкция установки и восстановления. В package не включать тестовые CFE,
базу .1CD/DT и реальные пользовательские данные без явной необходимости.

Для основной конфигурации оценить реструктуризацию, изменения данных и поддержку.
Для расширения — применимость к версии, порядок/зависимости, собственные данные.
Для EPF/ERF — запуск/регистрацию и права. Откат CF/CFE не всегда возвращает
преобразованные данные; проверять восстановление из резервной копии на стенде.

Полный цикл закончился, когда проверено ожидаемое поведение, получен нужный
артефакт, известна область проверки и воспроизводим запуск. Публикация/установка
в рабочую ИБ выполняется в пределах задания, а не вслед за каждым commit.
