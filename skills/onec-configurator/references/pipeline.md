## Быстрый путь: только 1cv8, без OneScript

Для запросов «собери», «проверь на платформе», «протестируй». Нужна установленная
платформа и **тестовая** база; OneScript и vanessa-runner не нужны.

```text
python "${CLAUDE_SKILL_DIR}/scripts/onec_env.py" discover
python "${CLAUDE_SKILL_DIR}/scripts/onec_env.py" setup --base "<имя тестовой базы из списка>"
python "${CLAUDE_SKILL_DIR}/scripts/onec_env.py" profile cf-check
```

1. `discover` показывает установленные версии платформы, базы из списка 1С
   (`ibases.v8i`), инструменты и источники проекта; отмечает версию, которая
   соответствует формату выгрузки (2.20 → 8.3.27, 2.21 → 8.5.1). Запускать из папки
   проекта или с `--project`. Ничего не запускает и не меняет.
2. Тестовую базу называет пользователь. Не выбирать её по списку самому, даже если
   имя похоже на тестовое: загрузка заменяет конфигурацию базы. Если в `CLAUDE.md`
   проекта или `.onec/env.json` база уже записана — повторно не спрашивать.
3. `setup` записывает выбор в `<проект>/.onec/env.json`. Платформа берётся по формату
   выгрузки, если подходит ровно одна сборка; иначе `--platform <версия>`. Ключи:
   `--base-file <каталог>`, `--base-server <сервер>/<база>`, `--user <имя>`,
   `--password-env <ПЕРЕМЕННАЯ>`. После `setup` дописать в `CLAUDE.md` проекта строку,
   которую он печатает.
4. `profile <вид>` создаёт профиль в `<проект>/.onec/pipelines/` и печатает готовую
   команду `pipeline.py` с новым каталогом `build/<вид>-NNN`. Сначала план, затем
   та же команда с `--apply`.

| Вид | Этапы |
|---|---|
| `cf-check` | загрузка выгрузки в тестовую базу → `/CheckConfig` |
| `cf-build` | то же → выгрузка `.cf` |
| `cfe-build --extension Имя` | загрузка расширения → проверка → выгрузка `.cfe`. Если расширения с этим именем лежат в нескольких каталогах (`discover` помечает «одноимённое»), профиль не строится — указать каталог: `--extension <путь>` |
| `epf-build [--object Имя]` | сборка `.epf`/`.erf` из выгрузок внешних обработок и отчётов |
| `yaxunit --extension Имя` | запуск тестов YAxUnit в тестовой базе (движок и тесты уже загружены) |

- `--update-db` добавляет `/UpdateDBCfg`: без него конфигурация БД не обновляется и
  изменения нельзя проверить в режиме предприятия. Обновление меняет структуру данных
  тестовой базы.
- Полная загрузка крупной конфигурации идёт долго (предел шага по умолчанию 2 часа,
  `--timeout`). Загрузка только изменённых файлов:
  `onec_env.py changed --root <cf> --git` (или `--newer-than <файл>`), затем
  `profile cf-check --list-file <список>`. Частичная загрузка идёт с `-listFile`,
  `-Format Hierarchical`, `-partial`; удалённые объекты она из базы не убирает.
- Режимы `/CheckConfig` берутся из `DefaultRunMode`: управляемое приложение —
  `-ThinClient -Server`, обычное — `-ThickClientOrdinaryApplication -Server`.
  Другие режимы: `--check-mode <Режим>` (можно несколько). `-ExtendedModulesCheck`
  по умолчанию не включён: на типовых конфигурациях он даёт много замечаний.
- Пароль в профиль не пишется: в команде стоит `${env:ПЕРЕМЕННАЯ}`, значение берётся
  из окружения при запуске и не попадает в план и отчёт. Переменную задаёт
  пользователь; не просить пароль в чате и не подставлять его в команду.
- Диагностика в каталоге прогона:

  | Этап | Файлы |
  |---|---|
  | Конфигуратор (`1cv8 DESIGNER`: загрузка, проверка, обновление, выгрузка, сборка EPF/ERF) | `<этап>.log` — журнал платформы (`/Out`), `<этап>.code` — код результата |
  | YAxUnit через `1cv8c` | `yaxunit.xml` — JUnit, `yaxunit.code` — код YAxUnit, `yaxunit.stdout.log` / `.stderr.log` |
  | Любой этап vanessa-runner | `<этап>.stdout.log` — журнал vanessa-runner, `<этап>.stderr.log`; у проверки и тестов — JUnit (`check-cf.xml`, `yaxunit.xml`) |
  | Каждый этап | `<этап>.stdout.log`, `<этап>.stderr.log`; сводка — `pipeline-report.json` |

  После провала читать журнал: `onec_env.py log <файл>` (кодировку определяет сам).
- Конфигуратор не подключится, если база открыта в другом Конфигураторе.

### Исполнитель vanessa-runner

Те же виды профилей можно выполнять через vanessa-runner 3.x, если команда им пользуется:
`setup ... --runner vrunner` делает его исполнителем по умолчанию, `profile <вид> --runner vrunner`
(или `1cv8`) выбирает для одного профиля. Нужны OneScript и vanessa-runner (руководство, раздел 8).
`discover` находит vanessa-runner: локальную установку проекта (`oscript_modules`), глобальную
рядом с OneScript, либо путь `setup --vrunner <src/main.os>`, и показывает его версию.

- Запуск: `oscript <vanessa-runner>/src/main.os <команда> [опции] <путь>` — без `.bat`-обёртки;
  опции перед позиционным аргументом, как в документации vanessa-runner 3.
- Каталог этапа — новый каталог прогона: `autumn-properties.json` проекта не подменит базу и версию
  платформы. Переменные `VRUNNER_*` и `RUNNER_*` из окружения убираются.
- Пользователь и пароль — через `VRUNNER_DBUSER` / `VRUNNER_DBPWD` процесса этапа (пароль из
  переменной, названной в `setup --password-env`), а не в командной строке.
- Соответствие: загрузка — `cf load` / `cfe load --no-update-db`; проверка — `validate syntax-check`
  с отчётом JUnit; `--update-db` — отдельный `infobase update`; выгрузка — `cf unload` / `cfe unload`;
  `epf-build` — `epf compile` во временной базе (тестовая не нужна; каталог с несколькими объектами
  собирается платформой напрямую); `yaxunit` — `test yaxunit`.
- `--increment` — инкрементальная загрузка самого vanessa-runner (его индекс изменений); `--list-file`
  передаётся как `--list`.
- Версия vanessa-runner — у 2.x другие команды; профили рассчитаны на 3.x и сверены с 3.0.2.

«Протестируй», когда автотестов в проекте нет: выполнить `cf-check` (или
`cf-build --update-db`), сообщить, что автоматических тестов нет, и дать шаги ручной
проверки в тестовой базе; предложить написать тесты (testing.md). Не называть
проверку Конфигуратором прохождением тестов.

Профили этого раздела собраны по документации командной строки и проверены на
заглушке платформы. Первый запуск на реальной платформе пользователя считать
проверкой самого профиля: при отказе читать журнал и сверять ключи со справкой
установленной версии (designer-cli.md).

## Назначение

`scripts/pipeline.py` выполняет доверенный JSON-профиль последовательными
процессами. Нужен Python 3.10+, сторонние библиотеки не требуются. 1С,
OneScript, vrunner и тестовые движки устанавливаются отдельно. Без `--apply`
команды не запускаются и каталог результатов не создаётся.

## Использование

1. Скопировать нужный пример из `assets/pipelines` в каталог проекта tools.
2. Заполнить точные пути, сборку платформы, имена объектов и тестовый стенд.
3. Прочитать команды, проверить `--help` установленных версий и разрешённую ИБ.
4. Просмотреть план, затем выполнить уже порученный запуск с `--apply`.

```text
python "${CLAUDE_SKILL_DIR}/scripts/pipeline.py" --config tools/1c-pipeline.json --project . --run-dir build/run-001
python "${CLAUDE_SKILL_DIR}/scripts/pipeline.py" --config tools/1c-pipeline.json --project . --run-dir build/run-001 --apply
```

После выполнения каталог нельзя использовать повторно: выбрать run-002 и т.д.
Это исключает принятие старого отчёта и автоматическое удаление прежней сборки.
В PowerShell при необходимости использовать `py -3` вместо `python`.

## Профили

| Пример | Операции |
|---|---|
| create-project | Новая ИБ, каркас конфигурации и пустого расширения в XML |
| build-cf | XML → новая ИБ → CheckConfig → обновление БД → CF |
| build-cfe | Основная конфигурация → CFE → проверка → загрузка/применимость |
| build-epf-erf | Основная конфигурация → сборка одной EPF и одной ERF |
| full-cycle | 32 этапа: все виды сборки, YAxUnit, тестовое расширение, тесты, выгрузка/сравнение CF/CFE/EPF/ERF |
| test-yaxunit | Тесты в заранее подготовленной ИБ через native клиент |
| test-vanessa-automation | UI через native клиент, VAParams и JUnit |
| test-oneunit | OneScript-тесты через OneUnit |

Сборочные профили используют CLI **vanessa-runner v3.0.2**, изученный по этому
тегу. Они не используют EDT/ibcmd. `--temp-db` из более новой документации
намеренно не требуется: ИБ создаётся в новом `${run}/ib`. Тестовые standalone
профили работают с указанной существующей тестовой ИБ. Имена/каталоги в примерах
условные; особенно сверять имя EPF/ERF с корневым XML.

Основная конфигурация в примере проверяется как ThinClient/Server. Для обычных,
толстых, веб-клиентов изменить `--mode` по проекту. Общий профиль не заявляет
проверку всех клиентов и всех прикладных сценариев.

## Схема профиля v1

Корень: `schema: 1`, необязательные name/variables/prepare/env_unset_prefixes,
обязательный непустой steps. Неизвестные поля отклоняются.

- `variables`: непустые строки. Подстановка `${имя}` рекурсивно разрешается;
  циклическая/неизвестная переменная — ошибка.
- Встроенные переменные: project (явный корень или каталог профиля), run
  (новый каталог), skill (каталог скилла), python (текущий интерпретатор).
- `prepare`: `{ "path": "${run}/config.json", "json": {...} }` создаёт JSON
  после подстановок. Только внутри нового каталога прогона.
- `${env:ИМЯ}` в `command` подставляется из переменной окружения только при
  запуске; в плане и отчёте остаётся имя. Незаданная переменная — ошибка до
  создания каталога прогона. Предназначено для пароля тестовой базы.
- `env_unset_prefixes`: убирает у дочерних процессов наследованные переменные
  с указанными префиксами. Примеры убирают VRUNNER_/RUNNER_, чтобы старое
  подключение/настройки не направили команды в другую ИБ.

Этап: уникальный id из букв/цифр/дефиса/подчёркивания; kind:
check/build/deploy/test/run; command — массив аргументов; cwd; положительный
timeout в секундах (по умолчанию 600); необязательные inputs, outputs,
stdout_json_status/stdout_json_equals, env (переменные окружения процесса этапа; `${env:ИМЯ}`
в значениях подставляется при запуске). inputs проверяются перед соответствующим этапом,
поэтому могут быть результатом предыдущего. Относительные inputs и пути
исполняемых файлов разрешаются относительно cwd этапа, относительный cwd —
от project. Все этапы выполняются по порядку.

`command` не является shell-строкой: перенаправления, &&, переменные оболочки
не интерпретируются. Для .os указать oscript.exe и путь скрипта; для .ps1 —
PowerShell с `-File`. Прямые .bat/.cmd/.ps1/.sh отклоняются. Наличие оболочки
в argv не превращает доверенный профиль в безопасную песочницу.

`cwd` должен существовать либо быть равным `${run}`. Сборочные профили используют
новый cwd, чтобы не читать случайный autumn-properties.json проекта. У OneUnit
cwd = project для корректного поиска локальных зависимостей oscript.cfg.

## Доказательства outputs

| kind | Проверка |
|---|---|
| file | Файл существует, непустой по умолчанию; размер и SHA-256 |
| exitcode | Новый текстовый файл содержит 0; UTF-8/BOM или UTF-16 с BOM |
| junit | Валидный XML, testcase, нет failures/errors, согласованы счётчики |
| junit-dir | Рекурсивно все *.xml в новом каталоге, общий итог JUnit |

Пути результатов только внутри run, ссылки/junction не принимаются. Файл,
существовавший до своего этапа, не является доказательством. JUnit ограничен
32 MiB на файл и не поддерживает DTD/ENTITY. Отчёты только с агрегатами без
testcase не подходят для бизнес-тестов: нужен полный отчёт/адаптер движка.

`min_tests` — минимум **выполненных**, без skipped; для test по умолчанию 1
и не может быть 0. Установить проектный минимум. `max_skipped` по умолчанию 0.
Для check допустим min_tests=0: CheckConfig может выдавать пустой список замечаний;
это не означает выполнение нуля бизнес-тестов с успешным результатом.

`stdout_json_status` — перечень допустимых status из JSON stdout. Для инспектора
по умолчанию профиль принимает только ok; partial/no_input нельзя пропустить
как полноценный аудит. Возможные warnings разбираются по правилам проекта.

`stdout_json_equals` — ожидаемые скалярные значения полей верхнего уровня JSON.
Например `{ "changes_total": 0 }` требует отсутствия файловых отличий после
повторной выгрузки. Типы и значения должны совпасть; отсутствующее поле — ошибка.
Это строгий контроль байтов, не доказательство семантической эквивалентности.

`create_parent` — необязательный JSON boolean, по умолчанию true. Значение false
оставляет создание родительского каталога вызываемому инструменту. Это нужно
адаптеру генераторов, который сам требует новый каталог результата; остальные
проверки существования/свежести и ограничения пути сохраняются.

`allow_empty` принимает только JSON boolean. Пути outputs/prepare и всех
журналов заранее проверяются на пересечения файл/каталог. Родитель каталога run
может быть ссылкой, выбранной пользователем; внутри run ссылки не принимаются.

## Отчёты, остановка, границы

Каждый этап сохраняет stdout/stderr, время, код процесса и проверенные outputs.
`pipeline-report.json` — сводка; `pipeline-junit.xml` — результаты **этапов**,
не замена JUnit бизнес-тестов. Хранить оба уровня. После ошибки следующие этапы
имеют blocked; повторный автоматический прогон не маскирует исходный провал.

Коды CLI: 0 — план или успешно выполненные настроенные этапы; 1 — провал
прогона; 2 — неверный профиль/окружение. Значение passed относится только к
указанным этапам. Build-only профиль не подтверждает бизнес-тесты.

Таймаут останавливает группу процессов на POSIX; на Windows используется
taskkill по PID с дочерними процессами. Уже запущенная серверная операция или
отделившийся процесс может продолжаться. После аварии проверить ИБ и активные
сеансы; автоматический rollback данных и автоматическая очистка ИБ отсутствуют.
Запускатель не мешает внешнему редактору менять файлы во время прогона.

Не хранить пароли в variables/argv/JSON: план показывает команды, а сторонние
инструменты могут вывести секреты в лог. Для пароля использовать `${env:ИМЯ}` либо
принятый способ аутентификации стенда. Профиль и запускаемый код должны быть доверенными.
