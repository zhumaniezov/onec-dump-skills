# 1С: разработка по выгрузке Конфигуратора

Работать с существующей моделью и проверяемыми контрактами. Прослеживать связи
«метаданные → модуль → вызовы → данные → проверка». EDT не требуется.

## Начало задачи

1. Прочитать инструкции проекта и текущие изменения. Определить режим:
   **анализ** — чтение; **реализация** — правки в порученном объёме; **ревью** —
   дефекты с доказательствами; **инструкция** — шаги для Конфигуратора.
   Указание «только изучи» исключает правки и запуск изменения данных.
2. Найти корни основной конфигурации, расширений, внешних объектов. Установить
   сборку платформы, совместимость, вид клиента, версию конфигурации/БСП и формат
   выгрузки. Версия XML или прикладного решения не является сборкой платформы.
3. Найти определения, аналоги проекта, вызывающий код, подписки, перехватчики.
   Для вопроса о видимости поля проверить начальное свойство и все его изменения.
4. Выбрать 1–3 справочника ниже; не загружать весь комплект заранее.
5. Выполнить минимально достаточное решение. Факты подтверждать путём/строкой
   или источником, гипотезы отделять. Сначала извлекать сведения из проекта,
   спрашивать только то, что меняет решение.

## Рабочий контракт

- Изменять необходимые файлы; сохранять существующие UUID, идентификаторы типов
  и форм, пространства имён, порядок, BOM и окончания строк. Новые идентификаторы
  создавать только для действительно новых сущностей.
- Проверять точный тип API, сигнатуру, контекст и версию. Вызовы БСП и прикладных
  модулей сверять с исходниками данного проекта.
- При файловой правке сначала проверить diff и исходный хеш. Устаревший план
  перестроить по текущему файлу; не обходить отказ подстановкой нового хеша.
  Для нового объекта проверить владельца, состав, ссылки и новые идентификаторы.
- XML-парсинг, BSL LS, проверка Конфигуратора и выполнение сценария дают разные
  доказательства. Один результат не подменяет остальные.
- В запросе определить смысл и ключ строки; оптимизацию подтвердить равенством
  результатов. Перенос условия в `СрезПоследних` может изменить смысл.
- Для записи регистра определить область замещения, старый и новый ключ,
  коллизии и конкурентную запись. `Записать(Ложь)` не является универсальным update.
- Git pull меняет файлы. Загрузка в ИБ и обновление конфигурации БД — отдельные
  операции с выбранной базой/расширением. Учитывать уже данное разрешение.
- Без установленной 1С продолжать файловую работу и перечислить оставшиеся
  проверки. Не требовать EDT или платный MCP для обычной разработки.
- Для MVP использовать существующие точки расширения и минимальное число модулей.
  Локальный дубль оценивать по цене сопровождения; не перестраивать весь проект.
- Для полного цикла выбрать проверки по риску изменения: статические, сборка,
  контексты платформы, применимость расширений, бизнес-тесты, UI. Нулевой набор,
  старый отчёт и успешный запуск процесса не подтверждают прохождение тестов.
- Выбирать уже применяемый тестовый движок; Vanessa необязательна. OneScript
  проверяет свои скрипты, API информационной базы проверяется внутри 1С.
- Масштабировать процесс по риску: точечная правка — краткий маршрут; изменение
  модели данных, прав, обмена или несколько артефактов — карта изменений и этапы.
  Не добавлять согласование каждого шага, если задача и стенд уже определены.
- При неполной выдаче инструмента проверить total/truncated/findings. Отсутствие
  найденного метода не доказывает его отсутствия при пропущенных файлах.

## Инструменты

Python 3.10+ (на Windows `python`, иначе `python3`):
`python "${CLAUDE_SKILL_DIR}/scripts/<скрипт>" <команда> ...`. Без Python — точечные
Read/Grep/Glob. Большие XML (`Configuration.xml`, `ConfigDumpInfo.xml`) целиком не читать.

| Задача | Скрипт и команды | Справочник |
|---|---|---|
| Карточка объекта, «где используется», вызовы метода, поиск (сначала `build`; расширения и внешние обработки — `build --with <каталог>`) | `onec_index.py build/info/refs/find` | navigation.md |
| Запросы модулей, СКД, динамических списков: таблицы, поля, #std657/#std436/#std435 | `onec_query.py scan/show` | queries.md |
| Обычная форма `Form.bin`: элементы, обработчики, правка модуля | `ordinary_form.py info/module/set-module/verify` | navigation.md |
| Инвентаризация, аудит кодировок и EOL, снимки до/после | `dump_tool.py inventory/inspect/audit/snapshot/compare` | tooling.md |
| Стандарты ИТС офлайн: текст пункта, поиск по теме, стандарт по коду проверки | `onec_std.py show/find/diag` | bsl-standards.md |
| Окружение, сигнатуры методов и API БСП | `project_context.py doctor/api` | project-context.md |
| Точная правка XML/BSL: plan → show → apply → `--apply` | `source_edit.py` | source-edit.md |
| Каркасы закреплённым генератором в новый каталог | `generator_bridge.py` | generator-bridge.md |
| Сборка и тесты по профилю | `pipeline.py` (без `--apply` — только план) | pipeline.md |

- Ни один скрипт не заменяет XSD, компилятор и проверку платформой.
- `source_edit.py` сохраняет байты вне изменения; это не универсальный редактор
  метаданных и не способ автоматически менять UUID.
- Результат генератора проверить и только затем включать в проект.
- Перед `pipeline.py --apply` проверить целевую ИБ, версии и разрешённый объём;
  шаблон профиля не означает проверки на платформе пользователя.

## Завершение

Выдать **результат → изменённые объекты/файлы → доказательства проверки → что
остаётся проверить в 1С**. Для анализа: **вывод → цепочка вызовов и условий →
места в коде → неопределённости**. Для ревью сначала дефекты с последствиями,
затем стиль. Для инструкции указать точные шаги и ожидаемый результат.
Не обещать совместимость, ускорение или полную проверку без доказательств.
