# source_edit.py — полная спецификация (для разработчиков комплекта)

Агенту при работе достаточно `skills/onec-configurator/references/source-edit.md`. Здесь — полный контракт: формат плана, журнал, откат, лимиты.

`scripts/source_edit.py` — авторский инструмент Python 3.10+ (только стандартная
библиотека) для локальных текстовых выгрузок Конфигуратора. Он формирует
проверяемый план, затем применяет его только с явным `--apply`. XML не
пересериализуется: меняется конкретный текстовый диапазон, остальные байты
сохраняются. Никаких сетевых запросов, внешних процессов, паролей и действий
с информационной базой инструмент не выполняет.

Проверка XML означает корректность **синтаксиса**. Проверка схемы платформы,
загрузка в Конфигуратор, компиляция BSL и тестирование конфигурации не выполняются.
Их следует запускать отдельно после проверки diff.

## Команды

Из корня проекта с установленным комплектом:

```bash
python .claude/skills/onec-configurator/scripts/source_edit.py plan --project ./src/cf --request ./change.json --out ./change.plan.json
python .claude/skills/onec-configurator/scripts/source_edit.py show --plan ./change.plan.json
python .claude/skills/onec-configurator/scripts/source_edit.py apply --project ./src/cf --plan ./change.plan.json --journal ./change.journal
python .claude/skills/onec-configurator/scripts/source_edit.py apply --project ./src/cf --plan ./change.plan.json --journal ./change.journal --apply
```

`plan` не меняет исходники и создаёт исключительно явно указанный **новый** файл
плана. Путь вывода не может совпадать с целевым исходником. Повторный план
сохраняйте под новым именем. `show` проверяет внутреннюю согласованность плана
без чтения проекта и выводит план с diff и payload. `apply` без `--apply`
проверяет план и актуальность исходников, возвращает `dry_run` и ничего
не создаёт, включая каталог журнала. `--journal` обязателен и в этом режиме.

Все рабочие результаты и ошибки идут в stdout как JSON. Коды завершения:
`0` — успех/предварительная проверка; `1` — ошибка применения с отчётом об
откате; `2` — некорректный ввод, нарушенные предусловия или ошибка до применения.
`--help` выводит обычную справку argparse. `platform_validation` всегда `not_run`.

## Запрос: точная схема 1

Корневой объект содержит только `schema` (целое `1`, не boolean) и
`operations` (массив из 1–256 операций в порядке выполнения). Неизвестные поля,
повторяющиеся JSON-ключи, NaN и Infinity отклоняются.

| Операция `op` | Обязательные поля, кроме `op` | Необязательные поля |
|---|---|---|
| `replace-text` | `path`, `expected_sha256`, `old`, `new` | `expected_count`, по умолчанию `1` |
| `create-text` | `path`, `content`, `encoding`, `eol` | Нет |
| `xml-set-property` | `path`, `expected_sha256`, `property`, `expected_old`, `new` | Нет |

Все значения в таблице — строки, кроме `expected_count`, который должен быть
строго положительным целым числом; `true`/`false` не допускаются. `old` не может
быть пустой строкой. `expected_sha256` — SHA256 **исходных байтов**, ровно 64
строчных шестнадцатеричных символа. Хеш вычисляется до любого изменения:

```bash
python -c "import hashlib,pathlib; print(hashlib.sha256(pathlib.Path('src/cf/Module.bsl').read_bytes()).hexdigest())"
```

`path` — относительный путь от `--project` с `/` в качестве разделителя.
Поддерживаются только `.xml`, `.bsl`, `.os`, `.query` без учёта регистра суффикса.
Абсолютные пути, `.`/`..`, пустые сегменты, Windows drive/UNC/backslash-пути,
двоеточия, NUL, конечные пробелы/точки сегментов, `.git`, ссылки, junction и
reparse points в любом существующем предке запрещены. Регистр пути должен
точно совпадать с существующим; коллизии после case-fold отклоняются.
Родительские каталоги должны существовать: инструмент не создаёт структуру
выгрузки. Удаления и переименования не поддерживаются.

Повторные операции над одним существующим файлом выполняются последовательно
в памяти, а все их `expected_sha256` должны совпадать с единственным исходным
хешем файла. Для `replace-text` поиск — точный, регистрозависимый, без регулярных
выражений; количество неперекрывающихся совпадений обязано быть равно
`expected_count`. `new` может быть пустым. Для нового файла `create-text`
требует отсутствия цели и не принимает `expected_sha256`. Повторное создание
того же файла и редактирование созданного файла в том же запросе отклоняются:
сразу укажите окончательное содержимое в `content`.

### Кодировка и окончания строк

Существующие UTF-8, UTF-8 с BOM, UTF-16LE с BOM и UTF-16BE с BOM сохраняются
побайтно вне изменяемого диапазона. Другие кодировки, UTF-32 и NUL в тексте
отклоняются; кодировка без BOM не угадывается. Для UTF-8 BOM не добавляется
автоматически. В `replace-text` строка `old` должна содержать точные исходные
окончания строк. Новые окончания строк из `new` приводятся к единственному
стилю файла (`LF`, `CRLF` или `CR`); при смешанном стиле вставка новых строк
отклоняется. Если исходных окончаний строк нет, используются указанные в `new`.

Для `create-text` обязательны:

| Поле | Допустимые значения |
|---|---|
| `encoding` | `utf-8`, `utf-8-bom`, `utf-16le-bom`, `utf-16be-bom` |
| `eol` | `LF`, `CRLF`, `CR` |

Все окончания строк в `content` приводятся к выбранному `eol`. Остальные
символы и наличие/отсутствие завершающего окончания строки сохраняются.

### Изменение скалярного свойства XML

`xml-set-property` принимает только XML-файл структуры
`MetaDataObject → единственный объект метаданных → Properties → property`.
Выбирается единственный **прямой** элемент `Properties`, затем единственное
прямое свойство по локальному имени. Одноимённые свойства дочерних объектов
не выбираются. Пространства имён поддерживаются; если разные пространства
создают неоднозначность локальных имён, операция отклоняется.

`expected_old` должен точно совпадать с декодированным XML-значением, включая
пробелы (без trim). Вложенные элементы, отсутствующее/дублирующееся свойство,
неоднозначная структура и инструкции обработки внутри свойства отклоняются.
Пустое `<Version />` допускается: для непустого значения оно раскрывается
с сохранением имени и атрибутов тега. CDATA заменяется экранированным текстом.
Комментарии внутри свойства сохраняются в прежнем порядке после нового
значения; комментарии за пределами свойства не меняются.

`&`, `<` и `>` экранируются автоматически. CR в новом логическом значении
записывается как `&#13;`; LF представляется исходным стилем EOL документа,
чтобы XML-нормализация сохранила логическое значение. Теги, пространства имён,
атрибуты, UUID и окружающее форматирование не генерируются заново. UUID
автоматически не меняются. Исходный и каждый промежуточный/итоговый XML
проверяются на синтаксис. DTD и объявления ENTITY запрещены, включая UTF-16;
консервативная проверка также запрещает их буквальное упоминание в комментариях.

## Формат плана и ограничения

JSON-план содержит только следующие поля:

| Поле | Значение |
|---|---|
| `schema` | Целое `1` |
| `tool` / `version` | `onec-source-edit` / `1.0` |
| `project_root` | Разрешённый абсолютный путь исходного проекта |
| `request` | Полный исходный запрос schema 1 |
| `changes` | Упорядоченный массив уникальных файлов по первому упоминанию |
| `platform_validation` | `not_run` |
| `integrity_sha256` | SHA256 канонического JSON остальных полей |

Каждый элемент `changes` содержит только `path`, `kind` (`modify` или `create`),
`before_sha256`, `after_sha256`, `before_b64`, `after_b64`, `diff`.
Для создания `before_sha256` и `before_b64` равны JSON `null`; прочие хеши —
SHA256, payload — canonical Base64 полных байтов. `diff` — читаемый unified diff,
он не служит источником байтов для записи. Порядок `changes` восстанавливается
из запроса; дубликаты, несогласованные хеши, payload и diff отклоняются.
`show` и `apply` заново выполняют операции над исходным payload и сравнивают
все восстановленные поля с планом.

Канонический JSON для `integrity_sha256`: UTF-8,
`json.dumps(value, ensure_ascii=True, sort_keys=True, separators=(',', ':'), allow_nan=False)`
без поля `integrity_sha256`. Этот контроль обнаруживает случайное повреждение,
**не обеспечивает криптографическую аутентификацию**: человек, меняющий план и
все согласованные поля, может пересчитать хеш. Используйте доверенные локальные
планы и просматривайте diff. План является переносимыми данными, но применяется
только к тому же разрешённому корню проекта и тем же исходным SHA256.

Фиксированные пределы: 4 MiB на исходный и итоговый файл, 16 MiB на JSON-запрос,
64 MiB на JSON-план, максимум 256 операций. Размер ограничивается при чтении и
после преобразований; выход за пределы означает ошибку, а не успешную частичную
обработку. План содержит исходные и итоговые тексты: храните его согласно
требованиям проекта к исходному коду.

## Применение, журнал и восстановление

Перед первой записью проверяются **весь** план, корень, все пути, отсутствие
новых целей и исходные хеши всех существующих целей. Поэтому заранее устаревший
второй файл не приводит к изменению первого. Затем создаётся новый отдельный
каталог журнала (существующий каталог не используется), `backups/0000.bin` и
другие исходные копии, а также `report.json` с соответствием путей резервным
копиям. Журнал не может пересекаться с целевыми исходниками.

Файл готовится во временном файле соседнего каталога, данные flush/fsync,
затем повторно проверяются применимые предусловия непосредственно перед
публикацией. Для существующего файла используется атомарная `os.replace`,
для нового — атомарная hard-link публикация с запретом перезаписи. Если файловая
система не поддерживает hard links, создание завершается ошибкой; опасного
fallback на замену нет. Права существующего файла сохраняются, новый получает
режим `0600` с учётом возможностей ОС. ACL, xattr и файловые timestamps не
сохраняются как отдельный контракт.

При обычной перехваченной ошибке I/O или изменившихся предусловиях откатываются
только успешно опубликованные этим запуском файлы, в обратном порядке.
Перед откатом сверяются пути и **итоговые** хеши. Внешние изменения сохраняются:
для них отчёт содержит `rollback_conflicts` с путём, причиной и местом исходной
резервной копии (`null` для созданного файла). Восстановленные пути перечислены
в `rolled_back`; исходно опубликованные — в `completed`. Если не удалось убрать
служебный временный файл, его путь указан в `temporary_files`. Даже ошибка
очистки после успешной публикации учитывается при откате. Если запись отчёта
тоже завершилась ошибкой, полный отчёт остаётся в stdout, а причина —
в `report_write_error`. Не удаляйте журнал до ручного разрешения конфликтов.

Атомарность обеспечивается **для отдельного файла**, не для всей группы.
Остановка процесса/питания может оставить частично применённый набор: сверяйте
файлы с планом и резервными копиями. Инструмент не является песочницей и не
блокирует сторонние редакторы. Переносимая стандартная библиотека не даёт
атомарного compare-and-swap по содержимому: между последней проверкой и
публикацией/откатом остаётся короткое окно гонки. На время применения остановите
параллельные записи в эти файлы; проверки повторяются, но враждебный конкурентный
процесс не входит в модель защиты.

## Пример и проверка

`assets/source-edit.example.json` иллюстрирует три операции и содержит реальные
хеши следующей **синтетической** мини-выгрузки. Она не является проверенной
платформой конфигурацией. `Module.bsl` — UTF-8 без BOM, единственная строка
`Сообщить("Старое");` с завершающим CRLF. `Catalog.xml` — UTF-8 без BOM,
следующий текст в одной строке с завершающим LF:

```xml
<MetaDataObject xmlns="urn:synthetic:md"><Catalog uuid="00000000-0000-0000-0000-000000000001"><Properties><Name>Тест</Name><Version>1.0</Version></Properties></Catalog></MetaDataObject>
```

Перед использованием примера для реального проекта замените пути, значения и
хеши. Родительский каталог для `New.os` должен существовать; сам файл отсутствовать.
Автотесты используют временные каталоги, subprocess CLI, синтетический XML и
управляемые ошибки `os.replace`/`os.link`; они не запускают 1С и не подтверждают
компиляцию:

```bash
python -m unittest discover -s .claude/skills/onec-configurator/tests -p test_source_edit.py -v
```
